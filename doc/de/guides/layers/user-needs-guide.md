# Leitfaden zu Nutzerbedürfnissen

Ebene 3 von 7, Problemraum. Skill: `/layers-user-needs`.

## Wissen, was diese Ebene ist <a id="know-what-this-layer-is"></a>

- Was Nutzer erreichen wollen, und warum — eine Deutung von beobachtetem
  Verhalten und Domänenwissen
- Ergebnis: Chancen — Bedürfnisse, Schmerzpunkte, Wünsche

## Entscheiden <a id="decide"></a>

- Wer genau die Nutzer sind, und in welcher Situation
- Welche Aufgaben (Jobs) sie erledigen: funktional, emotional, sozial
- Welche Bedürfnisse belegt sind, welche angenommen
- Welche Bedürfnisse am meisten zählen, und warum

## Ehrlich bleiben <a id="keep-it-honest"></a>

- Das Bedürfnis benennen, nicht die Lösung; über „Ich will CSV
  exportieren“ hinausfragen
- Den Mechanismus weglassen: Das „Wenn“ darf das aktuelle System nicht
  nennen
- Das „Wenn“ vorstellbar machen: ein Ereignis, ein Gefühl, eine Schwelle
- Ausdrücklich nach emotionalen und sozialen Jobs fragen
- Konfidenz kennzeichnen: beobachtet / abgeleitet / angenommen

## Eine Technik wählen <a id="pick-a-technique"></a>

| Situation                       | Technik                                      |
| ------------------------------- | -------------------------------------------- |
| Standard                        | Job Stories: wenn, ich will, damit ich       |
| Team arbeitet rollenbasiert     | User Stories                                 |
| Große Nutzerbasis               | Top-Tasks-Analyse                            |
| Abstimmung mit Stakeholdern     | Persona plus Szenario                        |
| Messbarkeit ist wichtig         | ODI Desired Outcomes                         |
| Viele Bedürfnisse               | Priorisieren: Wichtigkeit × wie schlecht bedient |

## Festhalten <a id="capture"></a>

- Priorisierte Bedürfnisse mit Konfidenz
- Aufgedeckte, aber nicht priorisierte Bedürfnisse
- Lücken und Widersprüche zwischen Nutzertypen

## Weitermachen <a id="continue"></a>

zuerst zum [beobachteten Verhalten](observed-behaviour-guide.md)
